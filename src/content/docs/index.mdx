## SQL files and one YAML file

A pipeline is the SQL you would write anyway. `source()` reads an entity,
`sink()` writes one, `ref()` chains pipelines — and those template calls are
what `pz` compiles into a dependency-ordered DAG. No orchestration code, no
DSL, no scheduler config.

<div class="pz-cols">

```sql title="pipelines/orders_enriched.sql"
INSERT INTO {{ sink('lake', 'orders_curated',
                    strategy: 'replace', format: 'parquet') }}
select
    o.id,
    o.amount,
    c.email
from {{ ref('stg_orders') }} as o
join {{ source('raw', 'customers') }} as c
  on c.id = o.customer_id
```

```yaml title="connections.yml"
raw:
  connector: localfiles
  entities:
    customers:
      read:
        path: data/customers.csv
        format: csv

lake:
  connector: localfiles
  root: out   # writes land under out/<entity>/
```

## DuckDB is the hub

Sources land data into a local DuckDB staging database, SQL pipelines
transform inside it, sinks drain the results out. Data moves as zero-copy
Arrow batches — or never enters .NET at all when a connector can hand DuckDB
a native scan.

<span class="pz-kicker">Why pz</span>
## Built for pipelines you can trust

<CardGrid>
	<Card title="Incremental by declaration" icon="approve-check">
		`where cursor > {'{{ watermark(s, e) }}'}` is the whole incremental
		story. Watermarks advance only after every downstream sink commits —
		plus bounded backfill windows and CDC from Postgres and SQL Server.
	</Card>
	<Card title="Honest delivery guarantees" icon="seti:lock">
		Merge and replace are effectively-once; append is at-least-once, and
		the compiler makes you acknowledge duplicates before it will build
		that plan. The guarantee matrix is a documented stability contract.
	</Card>
	<Card title="Retries that reuse work" icon="rocket">
		`pz retry` re-runs a failed run without re-extracting what already
		landed and without re-writing sinks that already committed. Per-node
		retries, concurrency caps, and a circuit breaker are built in.
	</Card>
	<Card title="Data quality inline" icon="magnifier">
		`not_null`, `unique`, and custom SQL checks run as first-class DAG
		nodes in the same run as the data they check — failures block
		downstream writes instead of paging you afterwards.
	</Card>
	<Card title="Fast by architecture" icon="seti:db">
		DuckDB does the heavy lifting in-process; the .NET side only ever
		holds in-flight Arrow batches. Projection and predicate pushdown are
		extracted from your SQL and passed to capable connectors.
	</Card>
	<Card title="Observable runs" icon="setting">
		Every run emits a stable NDJSON event stream, OpenTelemetry traces
		and metrics, and a `run_results.json` artifact — the same contract
		whether you run locally or in CI.
	</Card>
</CardGrid>

<span class="pz-kicker">Quickstart</span>
## Running in five minutes

<Steps>

1. Install the CLI as a .NET global tool:

   ```console
   $ dotnet tool install --global Pz.Cli --prerelease
   ```

2. Scaffold a small, complete, runnable project:

   ```console
   $ pz init demo && cd demo
   ```

3. Run both flows — sources, pipelines, checks, and sinks in one command:

   ```console
   $ pz run --all
   ```

</Steps>

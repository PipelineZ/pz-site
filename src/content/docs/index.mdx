<span class="pz-kicker">The whole project</span>
## SQL files and one YAML file

A pipeline is the SQL you would write anyway. `source()` reads an entity,
`sink()` writes one, `ref()` chains pipelines — and those template calls are
what `pz` compiles into a dependency-ordered DAG. No orchestration code, no
DSL, no scheduler config.

<div class="pz-cols">

```sql title="pipelines/orders_enriched.sql"
INSERT INTO {{ sink('lake', 'orders_curated',
                    strategy: 'replace', format: 'parquet') }}
select
    o.id,
    o.amount,
    c.email
from {{ ref('stg_orders') }} as o
join {{ source('raw', 'customers') }} as c
  on c.id = o.customer_id
```

```yaml title="connections.yml"
raw:
  connector: localfiles
  entities:
    customers:
      read:
        path: data/customers.csv
        format: csv

lake:
  connector: localfiles
  root: out   # writes land under out/<entity>/
```

## DuckDB is the hub

Sources land data into a local DuckDB staging database, SQL pipelines
transform inside it, sinks drain the results out. Data moves as zero-copy
Arrow batches — or never enters .NET at all when a connector can hand DuckDB
a native scan.

<div class="pz-section">
<span class="pz-kicker">Why pz</span>
## Sound familiar?

Every one of these has paged somebody at 2 a.m. `pz` was designed around
them — not around a feature list.

<div class="pz-bento">
	<div class="pz-tile" style="--pz-card: var(--pz-green)">
		<p class="pz-tile-title"><i></i>The nightly full reload</p>
		<p>The job re-reads 40 million rows to pick up two thousand new ones,
		and the warehouse bill shows it. In pz, one where-clause makes the read
		incremental — and the watermark only advances after every downstream
		sink has committed, so a crash can't strand data.</p>
		<code class="pz-proof">where updated_at &gt; <b>{'{{ watermark(\'crm\', \'orders\') }}'}</b></code>
	</div>
	<div class="pz-tile" style="--pz-card: var(--pz-sky)">
		<p class="pz-tile-title"><i></i>Tuesday's revenue is double</p>
		<p>A retried batch replayed a slice into an append sink. Finance found
		it before you did. pz refuses to compile that plan without your
		signature on it.</p>
		<code class="pz-proof"><b>error PZ0214:</b> append fed by an incremental dataset — a replayed slice can duplicate rows</code>
	</div>
	<div class="pz-tile" style="--pz-card: var(--pz-blue)">
		<p class="pz-tile-title"><i></i>Failed at 5:47, on the last node</p>
		<p>And the rerun starts the whole four hours from zero. `pz retry`
		re-executes only what failed — staged data is reused, committed sinks
		stay committed.</p>
		<code class="pz-proof"><b>note:</b> reusing staged data for 2 source load(s)</code>
	</div>
	<div class="pz-tile" style="--pz-card: var(--pz-peach)">
		<p class="pz-tile-title"><i></i>The bad rows shipped a week ago</p>
		<p>The check that would have caught them lived in another tool, on
		another schedule. In pz, checks are DAG nodes in the same run — a
		failure blocks the writes downstream of it before anyone dashboards
		bad numbers.</p>
		<code class="pz-proof"><b>ok</b> check_orders_enriched_unique_id 0 rows 3ms</code>
	</div>
	<div class="pz-tile" style="--pz-card: var(--pz-red)">
		<p class="pz-tile-title"><i></i>A cluster to copy a CSV</p>
		<p>Moving a few gigabytes shouldn't need one. pz is a single process:
		DuckDB does the heavy lifting, .NET holds only in-flight Arrow batches,
		and connectors hand DuckDB a native scan when they can.</p>
		<code class="pz-proof">zero-copy Arrow · <b>native scan</b> when the connector can</code>
	</div>
	<div class="pz-tile" style="--pz-card: var(--pz-teal)">
		<p class="pz-tile-title"><i></i>"It succeeded." Succeeded at what?</p>
		<p>An exit code is not an audit trail. Every run emits a stable NDJSON
		event stream, OpenTelemetry traces and metrics, and a
		`run_results.json` you can diff — locally and in CI alike.</p>
		<code class="pz-proof">{'{'}"event":<b>"run_completed"</b>,"status":"success","succeeded":12{'}'}</code>
	</div>

<span class="pz-kicker">Quickstart</span>
## Running in five minutes

<Steps>

1. Install the CLI as a .NET global tool:

   ```console
   $ dotnet tool install --global Pz.Cli --prerelease
   ```

2. Scaffold a small, complete, runnable project:

   ```console
   $ pz init demo && cd demo
   ```

3. Run both flows — sources, pipelines, checks, and sinks in one command:

   ```console
   $ pz run --all
   ```

</Steps>
